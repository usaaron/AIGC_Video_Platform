# Reliability Gates

This file defines the current "iron triangle" that must stay green before production use.

## CI Gate

Pull requests and pushes to `main` run `.github/workflows/ci.yml`.

- `quality` runs format, lint, deprecated organization API checks, API unit coverage, workspace tests, and build.
- `database` starts Postgres 16 and Redis 7, applies migrations, then runs API contract, integration, and security tests.
- API unit coverage is generated by `pnpm test:backend:coverage`.
- The gate compares `apps/api/coverage/coverage-summary.json` with `apps/api/coverage-baseline.json` for historical regression tracking.
- `apps/api/coverage-policy.json` holds the overall 5% regression cap and the current core-module floors.
- Any `lines`, `statements`, `branches`, or `functions` drop of more than 5 percentage points fails CI.
- Current core floors are 80% on `src/core/auth/password.ts`, `src/core/auth/roles.ts`, `src/core/auth/authorization.ts`, `src/core/auth/sessionToken.ts`, `src/core/media/publicMediaToken.ts`, and `src/core/jobs/taskResourceLock.ts`.

Update `apps/api/coverage-baseline.json` only after an intentional coverage change has landed on `main`.
Update `apps/api/coverage-policy.json` only when the core floors or overall cap intentionally change.

## Synthetic Probe

The reusable read-only probe command is:

```bash
pnpm probe:synthetic
```

It performs these read-only or low-side-effect checks against the account's current organization:

- `GET /api/v1/health`
- `GET /api/v1/health/readiness`
- `POST /api/v1/auth/login`
- `GET /api/v1/auth/me`
- `GET /api/v1/projects`
- `GET /api/v1/billing/summary`

The post-deploy write-path probe command is:

```bash
pnpm probe:synthetic:write
```

It must only run against a dedicated non-system synthetic organization identified by
`SYNTHETIC_ORGANIZATION_ID`. The probe logs in as the synthetic monitoring account, verifies that
the account belongs to that organization, switches to it through `/api/v1/organizations/:id/switch`,
then runs a no-provider/no-billing write path:

- `POST /api/v1/projects`
- `PATCH /api/v1/projects/:id`
- `POST /api/v1/projects/:id/assets`
- `PATCH /api/v1/projects/:id/assets/:assetId`
- `POST /api/v1/projects/:id/shots`
- `PATCH /api/v1/projects/:id/shots/:shotId`
- `POST /api/v1/projects/:id/versions`
- `PATCH /api/v1/projects/:id` with `status=archived`

The internal system organization, currently `tenant-seqora-demo`, is explicitly rejected as a write
probe target.

Required environment:

```bash
SYNTHETIC_BASE_URL=https://zjh.ai
SYNTHETIC_EMAIL=monitoring@example.com
SYNTHETIC_PASSWORD=replace-with-monitoring-password
```

Optional environment:

```bash
SYNTHETIC_TIMEOUT_MS=10000
SYNTHETIC_ALERT_WEBHOOK_URL=https://monitoring.example.com/hooks/seqora
```

Write-path environment:

```bash
SYNTHETIC_ORGANIZATION_ID=tenant-synthetic-production
SYNTHETIC_PROBE_MODE=write
SYNTHETIC_REQUIRE_ALERT_WEBHOOK=true
```

Provisioning rule:

- Create one dedicated synthetic monitoring account.
- Add that account to one dedicated synthetic organization as `member` or `organization_member`.
- Do not reuse the internal system organization, owner account, customer organization, or C-end personal space.
- Store `SYNTHETIC_BASE_URL` and `SYNTHETIC_ORGANIZATION_ID` as GitHub environment variables.
- Store `SYNTHETIC_EMAIL`, `SYNTHETIC_PASSWORD`, and `SYNTHETIC_ALERT_WEBHOOK_URL` as GitHub secrets.
- Mirror the runtime-only VM values from `deploy/monitoring.env.example` into `/opt/seqora/deploy/monitoring.env`.

The probe is wired into:

- `.github/workflows/deploy.yml` as two post-deploy release gates: read-only first, then write-path.
- `deploy/bootstrap-gce.sh` + `deploy/systemd/seqora-synthetic-probe.timer` for a one-minute VM-side read-only probe.
- `.github/workflows/synthetic-probe.yml` as the scheduled read-only backup probe.

If `SYNTHETIC_ALERT_WEBHOOK_URL` is configured, failures post a JSON alert before exiting non-zero.
Production release and scheduled GitHub probes set `SYNTHETIC_REQUIRE_ALERT_WEBHOOK=true`, so a missing
webhook is treated as a gate failure. Any failed post-deploy probe marks the deploy workflow failed.

## Observability Verification

HTTP responses include both `x-request-id` and `x-trace-id`; they currently use the same request id value.

Request completion logs include:

- `requestId`
- `traceId`
- `tenantId`
- `userId`
- `taskId`
- `jobId`
- `projectId`
- `method`
- `route`
- `statusCode`
- `durationMs`

Metrics endpoints:

- `GET /api/v1/observability/metrics` returns the existing protected JSON snapshot.
- `GET /api/v1/observability/metrics/prometheus` returns protected Prometheus text format.

Tests enforce:

- TraceId appears in request logs.
- The Prometheus exporter marks counters and failure totals correctly.
- A 5xx readiness response increments the exported failure counter.
