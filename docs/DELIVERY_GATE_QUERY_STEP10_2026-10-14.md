# 交付门禁查询第十步：正式交付只读判定

2026-10-14，本地预览完成冻结合同后的服务端交付门禁查询。该步骤把“是否满足正式交付条件”收敛为服务器重新计算的只读结果，供生成队列核验弹层展示；没有引入发布、下载、Provider 调用或扣费动作。

## 已完成

- 共享契约新增 `deliveryGateResult`：返回 `allowed`、`blocked` 或 `pending`，并带稳定的原因码、说明、核验时间和底层验证快照。
- API 新增 `GET /api/v1/generation/tasks/:taskId/delivery-gate`，沿用任务读取权限和组织/项目/任务范围检查。
- 服务端每次查询都会重新读取任务和冻结合同，重算当前证据，并在视频任务上重新执行对象存储尾帧验证；客户端提交的结果不能直接放行。
- 门禁强制检查冻结合同及哈希、任务完成、主交付媒体可读性、内容验收、刚性物理验收、连续性尾帧和合同要求完整性。物理验收一旦存在失败，即使冻结合同省略 `physical-review`，仍返回阻断结果，避免通过删减合同要求绕过失败事实。
- 生成队列的“查看交付核验”弹层同时展示原有证据核验和正式门禁结果，并区分待补、失败和已允许状态。
- 终端任务的紧凑轮询投影保留 `deliveryContract`，不会因版本轮询把已冻结任务错误地切回“冻结交付合同”入口。

当前 `media-url` 仍只有观察事实，主视频本体可读性和尾帧连续性未通过时，门禁会保持 `pending` 或在同时存在硬失败时返回 `blocked`。这是证据不足的真实状态，不代表已完成正式交付。

## 真实浏览器核验

在 `http://127.0.0.1:5183/` 使用一次性本地临时夹具核验了完整入口：任务行显示“查看交付核验”，弹层能展示冻结哈希、证据状态、门禁状态和原因，并可关闭恢复队列。夹具刻意省略 `physical-review`，但保留已失败的物理审计；弹层仍显示“正式交付已被阻止”和“刚性物理验收失败”，证明服务端门禁没有被合同删项绕过。

走查结束后已停止临时 API、恢复原始 `app.json`，并按完整预览脚本重新建立 5183、8787、8190 以及管理端服务。原始数据哈希、任务时间和无冻结合同状态已核对；临时夹具数据已清理，不进入 Git。

## 下一步

1. 为主交付媒体增加对象存储本体可读取性、大小和哈希证明，不再只依赖尾帧观察事实。
2. 把该只读门禁接入正式发布/下载写边界，失败或待补时由服务端拒绝动作，并记录审计事件。
3. 补齐 Provider 完成回执、内容验收、物理验收、连续性和跨集合同步的生产数据来源，再验证允许路径。
4. 最后再设计发布确认、计费/扣费和批量集交付，继续保持不绕过组织权限、合同哈希和乐观并发。
