# 序幕 TV 产品闭环需求（B 端交付、资产复用与百集生产）

> 状态：需求整理稿，2026-09-13 按当前工作区代码核对；不是生产验收报告。
>
> 目标：明确 B 端账号交付、组织积分、账号资产库、人物自动加白和“一人一天一部剧”的业务闭环，作为后续实现和验收依据。

## 1. 产品目标

序幕 TV 需要同时支持两种使用方式：

1. 平台向企业、团队或项目组交付一个可立即使用的组织管理员账号。
2. 组织管理员自行创建测试账号或成员账号，分配组织额度，让成员独立登录使用。

创作侧的长期目标是：一个人完成一次项目配置和必要确认后，系统可以在后台持续生产约 100 集短剧，并且在任务失败、服务重启或用户离开页面后继续运行，最终交付分集视频和可追溯的项目资料。

用户已确认的目标与边界：

- 一部剧默认 100 集，每集约 60 秒，全剧约 100 分钟；
- 长剧本生成由用户团队后续接入，本次重点是现有功能之间的衔接；
- 声音随视频一起生成，成片能直接播放、下载，首版不要求字幕或独立配音；
- 一个人能管理全流程，用户最新确认的全链路生成目标为 1 天以内；以 24 小时以内作为产能验证目标，具体计时起止与人工确认等待的处理需在整合后明确；
- 本次未运行百集实测。此前 3 至 4 小时的口径不再作为需求；之前回复中的 8 至 20 小时也是未经实测的估算，不能作为当前产能结论。

以下章节中的积分分配、资产版本和自动化规则是推荐方案；已确认的产品目标与这些待实现的业务规则需分别验收。本轮暂停微信扫码和短信登录的开发，只整理需求；之前未完成的登录改动需在发布前单独处理。

## 2. 账号和组织模型

### 2.1 账号层级

| 层级     | 角色                   | 主要职责                                                |
| -------- | ---------------------- | ------------------------------------------------------- |
| 平台交付 | `owner`、`super_admin` | 创建组织、交付首个管理员、充值组织额度、处理异常和审计  |
| 平台运营 | `admin`                | 既有授权范围内的运营；不因此获得 B 端组织创建和充值权限 |
| 组织     | `organization_admin`   | 管理本组织成员、创建账号、分配配额、查看组织用量和资产  |
| 组织成员 | `organization_member`  | 创建项目、生成剧本/资产/分镜/视频，使用组织配额         |
| 个人     | `member`               | 独立使用个人空间和个人额度                              |

组织管理员不是平台管理员，不能创建或提权平台角色，也不能访问其他组织的数据。

### 2.2 B 端交付流程

平台 owner 或超级管理员在管理端执行：

```text
创建组织
  -> 创建首个组织管理员
  -> 给组织共享积分池充值
  -> 生成一次性账号交付信息
  -> 发送给客户
```

客户第一次登录后必须修改初始密码。平台数据库只保存密码哈希，后台不能查看既有密码。

组织管理员自助创建成员的流程为：

```text
组织管理员进入成员管理
  -> 单个填写或批量导入邮箱和显示名
  -> 默认创建 organization_member 并生成独立临时密码
  -> 设置初始配额（可选）
  -> 生成一次性交付信息
  -> 成员首次登录并修改密码
```

当前账号唯一标识为邮箱。首版沿用现有账号规则；若测试交付要求完全不使用邮箱、自动生成短账号，需要另增登录名契约，不能把虚构邮箱标记成已验证。已有账号加入组织只增加 membership，不能覆盖其原密码。批量创建要逐项返回成功或失败，重试不重复建号、不重复分配积分。

现有邀请码注册规则继续用于平台个人注册。组织交付使用受权限保护的代建账号流程，保留现有临时密码、首次改密、会话和审计机制。组织管理员只能管理本组织普通成员，不能创建同级管理员或影响该成员在其他组织的身份。

### 2.3 账号导出规则

“导出账号密码”只允许导出新创建账号的初始凭据，具体规则如下：

- 支持单个下载和批量 CSV 下载；
- 导出字段包括组织、账号邮箱、显示名、角色、初始密码、配额、创建时间和首次登录地址；
- 初始密码只在创建完成后的本次响应或一次性导出中出现；
- 后续再次导出只能导出账号信息和密码状态，不能恢复旧密码；
- 重置密码时生成新的临时密码，并再次提供一次性下载；
- 导出、创建、重置、禁用和删除都写入审计日志；
- 导出文件不得进入普通项目资产库、任务日志、错误日志或对象存储长期目录。

本次测试和客户交付的主流程是直接建号并导出临时密码，邀请链接保留为可选方式。导出响应不缓存、不持久化明文密码；下载丢失后走显式重置。重置已有跨组织账号的全局密码不能仅凭当前组织成员身份授权。

## 3. 积分和配额

### 3.1 推荐的记账模型

B 端资金和额度归组织，不归组织管理员个人。组织拥有一个组织共享积分池：

```text
组织未消费积分总额 = 组织可分配余额 + 所有成员可用积分之和 + 任务冻结积分
```

组织管理员设置成员积分时，从组织可分配余额划出对应额度，成员只消费分给自己的部分；管理员自己的创作从组织可分配余额扣款，不能动用已经分给其他成员的额度。分配是内部转移，不算生成消费，也不能创建一笔没有资金来源的个人充值。

例如充值 10,000 积分后给成员分配 3,000：管理员可分配 7,000，成员可用 3,000，组织仍拥有 10,000。成员提交 100 积分任务后，成员可用 2,900、冻结 100；成功结算后组织未消费总额为 9,900，不能再次扣一遍。失败退款恢复原扣款来源。

禁用成员时阻止新任务并回收未冻结余额；运行中任务继续结算，其后退款进入组织可分配余额，不能提前回收冻结积分导致重复发放。撤销成员后保留账本、项目和已产出资产。

这样可以实现用户提出的“管理员设置积分，消耗管理员可管理的额度”，同时避免把企业购买的积分错误记成管理员个人资产。现有账单代码已经有组织共享池概念，后续应在其上增加成员配额，而不是重新建立一套个人充值逻辑。

### 3.2 积分规则

- 充值、赠送、调账、分配、消费、退款和退回都必须进入不可变账本；
- 组织管理员只能分配、回收本组织的现有额度，不能用调账接口增加组织总额度；现有通用调账权限必须一起收紧，不能只隐藏页面按钮；
- 服务端根据任务类型和参数定价，客户端提交的预估价格不能决定真实扣费；
- 创建批量生产任务前展示预计消耗、余额、预计并发和可能的失败退款规则；
- 批量任务按阶段或分集预扣，完成、失败、取消时逐项结算；
- 分配、回收、预扣、结算和退款使用数据库事务及幂等键，禁止负余额和并发超分配；
- 组织管理员能查看组织总用量和成员用量，成员只能查看自己的用量；
- 组织账单、个人账单和支付页面保持边界，B 端充值仍由平台后台或正式企业支付流程完成。

给成员“设置余额”必须显示调整差额、可分配余额和结果；推荐提供增加/回收操作以减少覆盖误差。余额和并发是独立权益，不能通过批量开账号无限扩大组织并发。迁移现有共享池时核对余额、在途任务和历史会员权益，不追溯扣费或发放重复赠送积分。

## 4. 资产库

### 4.1 产品定义

资产库是账号或组织范围内的长期资产目录，用于跨项目查看、复用、版本管理和追溯。项目内资产是当前项目的使用副本或引用，资产库中的资产是可复用的长期版本。

当前代码已有资产库表、分类、版本、回收站、去重和下载。导入项目目前仅支持图片、音频和剧本文本，人物/场景类型仍会被拒绝。主要缺口是生成结果自动归档、在生成资产的状态展示、历史资产补录，以及人物/场景完整结构的跨项目复用。

### 4.2 自动归档规则

资产创建后即进入当前账号、当前组织范围的资产列表，显示未生成、排队、生成中、失败等状态；成功后由 Worker 把持久化输出登记到相应资产版本。这样生成中也能找到资产，失败记录不会假装成可用素材。

| 生成结果                         | 资产库行为                                                     |
| -------------------------------- | -------------------------------------------------------------- |
| 人物面部、全身、三视图           | 归档为同一人物的阶段版本或子版本，保留源项目、任务和提示词快照 |
| 场景                             | 自动归档为场景资产，并按名称、标签和源项目分类                 |
| 物品、服装、品牌                 | 自动归档为对应类型资产                                         |
| 独立图片、音频、视频、成片       | 按媒体类型归档，可新增版本                                     |
| 任务失败、取消或只有临时中间结果 | 保留资产条目及任务状态，没有成功输出时不标为可用               |

自动归档必须幂等，以组织、资产、任务和输出标识去重；不同输出保留为候选或历史版本，不能只保存最后一张。文件可按内容去重，不凭同名合并两个人物。人物面部、全身、三视图归在一个人物条目下，并记录选中的基准版本。

已有账号的历史项目资产要补录，支持重复运行和进度追踪。归档失败单独重试，不把成功的图片任务改成失败或再次扣费。图片完成后资产归档与加白分别执行，彼此失败不应阻止另一项。

### 4.3 资产可见范围

- 首版“我的资产”：当前组织内该账号所有项目的资产，与个人空间及其他组织隔离；
- 同组织成员不会仅因为共用积分就自动互相看到全部素材；组织共享库作为后续授权能力，不强制加入首版；
- 组织管理员查看成员资产遵循已有内容权限，不能从供应商全局素材列表推断本组织所有权；
- 删除项目不级联删除归档媒体，保留源项目 ID 和名称快照；资产回收站不破坏已经锁定的项目版本及历史成片；
- 资产必须保留 `sourceProjectId`、`sourceTaskId`、创建人、版本、提示词快照和当前状态；
- 项目使用资产时记录使用的具体版本，后续资产库更新不能悄悄改变已提交任务。

### 4.4 资产复用流程

```text
资产库选择人物/场景/物品
  -> 选择具体版本
  -> 导入当前项目
  -> 项目保存 libraryItemId + version
  -> 分镜和视频任务使用锁定版本
```

人物、场景等不能只依赖名称匹配。后续应为可复用实体增加稳定的资产库 ID，项目内显示名称可以修改，但不能破坏实体关联。

## 5. 人物自动加白

“自动加白”与“进入资产库”是两个不同动作：前者是把人物注册到视频 Provider 的可信人像素材库，后者是平台自己的长期资产归档。

### 5.1 自动加白触发条件

推荐采用以下规则实现用户提出的“生成好了自动加白”：成功生成并选定为当前基准的人物面部，通过基础检查后自动建立基准并提交注册，不再要求额外点击加白。已有多个候选或用户正在手动编辑时，不擅自替换已确认基准，确认新基准后自动重新注册。

自动注册条件：

- 已有锁定的面部基准图及其版本；
- 项目或人物类型需要可信人像；
- 图片来源符合 Provider 的素材规则；
- 当前组织和账号具有对应 Provider 能力；
- 没有同一人物和同一基准图的进行中或已完成注册任务。

CG、2D 或不需要真人一致性的角色只自动进入资产库，不强制进入可信人像白名单。已授权真人仍必须走本人完成的活体认证流程，平台不能替代本人认证。

### 5.2 状态和使用规则

```text
人物基准生成完成并锁定
  -> 创建可信人像注册任务
  -> processing
  -> active / failed
```

- `processing` 显示加白中；批量流程可保留等待依赖，只有 `active` 才允许向视频 Provider 提交，等待阶段不开始视频消费；
- `active` 才能转换为 `asset://<providerAssetId>` 并用于需要可信人像的视频；
- `failed` 必须展示失败原因、重试入口和最近一次尝试时间；
- 自动加白失败不能回滚已经成功的人物资产，但需要阻止依赖该白名单的视频任务；
- 注册任务必须后台执行，不依赖人物编辑器页面保持打开；
- 组织内复用时使用同一个已授权 Provider 资产，但必须继续做组织权限和状态校验。

加白状态绑定具体面部版本和 Provider；换脸、切换供应商时旧状态不能沿用。旧注册任务晚到的回调不能覆盖新基准。自动化中需要记录实际加白费用、失败退款和重试上限，纳入生产预算。

## 6. 一人一天一部剧的生产链路

### 6.1 生产对象

已确认的交付规格与建议的制作规则：

- 100 集；
- 每集约 60 秒；
- 每集场次和镜头数由实际输入决定，不为凑数固定为 6 至 8 场；
- 每个可制作镜头 3 至 15 秒；
- 每集有明确的目标、冲突、变化和结尾钩子；
- 角色、场景和关键物品使用稳定实体 ID；
- 任何阶段都能按集、按场次或按镜头重试。

### 6.2 阶段与依赖

用户明确要求依据现有链路执行生成任务。以当前项目的“项目 → 剧本/分集 → 资产 → 分镜 → 生成队列 → 成片预览/下载”为产品与执行主线；下方流程是各阶段的接入与补齐规则，不是新增一套生产流程。

```text
接入长剧本/对应分镜
  -> 校验分集、实体、镜头、时长与声音内容
  -> 展示资产与样片预算并确认
  -> 复用或生成资产，自动归档，人物自动加白
  -> 锁定镜头及资产版本，确认预算和样片
  -> 分集批量生成有声视频
  -> 每集镜头齐全后保留音轨合成
  -> 播放、单集下载、全集批量下载
```

每个阶段必须保存输入版本、输出版本、任务 ID、开始/结束时间、消耗积分、失败条目和人工确认记录。阶段失败只阻塞相关依赖，不让整部剧回滚。

复用现有 Agent 的阶段模型和生成任务状态，扩展百集适配与按集恢复，不新建平行任务系统。已有分镜只校验和映射，不重复调用分镜生成；只有缺失项调用现有功能补齐。完成一批依赖后即可推进后续阶段，不强制等全剧资产完成才开始第一集。

保持每集首镜独立；需要尾帧连续的镜头在集内串行，不同集可并发。全剧角色、服装和声音要求由稳定实体和版本保持，不能把 100 集全部串成一条尾帧链。人脸一致性之外，台词遗漏、音色漂移和声音断点也要抽检。

### 6.3 用户操作和系统操作

用户需要完成：

1. 接入长剧本和分镜，确认视觉风格、集数和单集时长；
2. 确认大纲和主要角色/场景清单；
3. 确认资产及样片预算，生成并检查第一集样片；
4. 查看剩余预算并确认批量生产；
5. 处理异常资产、白名单失败和质量门禁；
6. 最终下载分集和项目交付包。

本项目负责自动完成：

- 接收长剧本模块的分集、实体及分镜结果，校验编号、引用和版本；
- 人物、场景、物品去重和资产库归档；
- 人物可信人像注册和状态轮询；
- 分镜编译、连续性上下文和镜头时长校验；
- 视频任务排队、并发、依赖、重试、退款和断点续传；
- 每集音画合成、版本记录和按集批量下载；字幕与独立音频导出不列为首版必要功能。

首版不把字幕作为交付前置条件。声音是必需交付物：视频生成和合成必须保留对白、环境声或音乐中的可用音轨；没有可用音轨时要明确标记失败或待处理，不能静默生成无声成片。

### 6.4 质量门禁

批次计划需要校验结构和预算；每一批实际提交视频 Provider 前必须满足：

- 分集编号连续且唯一；
- 每集有剧本、场次、镜头和结尾钩子；
- 镜头依赖的实体和资产版本可解析，不把缺失人物悄悄替换成纯文本生成；
- 本批镜头需要的可信人像均为 `active`，其他批次可继续等待；
- 预计积分不超过当前付款来源的可用额度，成员不能借用其他成员余额；
- 当前 Provider、队列和对象存储容量满足提交条件。

完成交付前必须通过：

- 每集视频可播放，时长和编号正确；
- 每集都有可用音轨，没有音轨时明确标记并阻止首版交付；
- 失败集、重试集和最终版本可追溯；
- 生成任务、积分流水、资产版本和交付文件可以相互关联。

下载文件按 E001 至 E100 排序，支持失败下载重试和分批打包。版本重生只使依赖它的镜头或集数需要更新，不覆盖用户已选定的历史成片。首版的“带声音”要求是场景所需对白/环境声可听、无明显截断，不能仅靠文件中有音频流就判定合格。

## 7. 当前实现与缺口

### 已有基础

- 组织、组织管理员、组织成员和组织共享积分池模型；
- 管理端已有“创建企业组织+首个管理员”、组织成员邀请和直接建号，需补齐批量交付体验；
- 个人/组织账单范围和生成并发控制；
- 项目内人物、场景、物品、服装资产；
- 资产库表、版本、回收站、去重、下载，以及图片/音频/剧本导入；
- 人物可信人像 Provider 注册、状态刷新和视频任务前置校验；
- 网剧分集、自动分镜、任务依赖、重试、退款和成片预览基础；
- 长剧本 JSONL、分批、幂等和断点续传协议草案。

当前 `core/film/filmPreviewComposer.ts` 已使用音视频一起拼接并输出 AAC，缺失音轨时填充静音，相关测试检查不带 `-an`。旧 `CURRENT_STATE.md` 和交接文档里的“整片无声”不能代表当前工作区实现；生产是否部署该版本及实际声音质量本轮未验证。

### 上线前必须补齐

1. 串联现有 B 端组织交付功能，补一次性凭据导出和部分失败恢复。
2. 组织管理员批量创建成员、设置配额、重置临时密码和导出账号清单。
3. 成员积分分配账本、冻结/退回，以及组织管理员调账权限收紧。现有 `canManageOrganizationBilling()` 允许本组织管理员调账，`recordAdjustmentForMembership()` 直接改成员账户余额，均不能代替守恒分配。
4. 生成任务成功后的自动资产库归档和跨项目版本复用。
5. 人物生成完成后的自动可信人像注册、幂等、防重复和失败重试。
6. 扩展现有编排支持 100 集和单集重试。当前 Agent 总时长契约上限 300 秒，planner 的估算镜头数上限 120，不能仅设置集数为 100 就支持总长 6,000 秒。
7. 验收现有带音轨合成，补声音异常提示、按集自动合成和全集下载，处理合成任务的资源上限。
8. 按用户团队后续提供的协议接入长剧本与对应分镜，保留输入版本和稳定实体 ID。
9. 按 Provider 实际延迟、失败率、并发上限和积分成本完成 3 集、10 集、100 集压测。

## 8. 上线验收场景

### B 端交付

1. 平台创建一个组织并充值组织共享积分。
2. 平台创建首个组织管理员并导出一次性凭据。
3. 管理员首次登录后修改密码。
4. 管理员创建 3 个成员账号，分别设置不同配额并导出凭据。
5. 成员只能看到本组织授权内容，不能访问平台后台或其他组织。
6. 成员提交生成任务后，组织池和成员配额流水正确扣减。
7. 禁用成员后回收未冻结余额，在途任务独立结算，不能重置成员在其他组织的身份。
8. 组织管理员请求通用充值/调账 API 不能凭空增加积分；批量分配同时提交也不能透支。

### 资产和人物

1. 生成一个人物、场景和物品，任务完成后自动出现在对应分类。
2. 刷新页面或重新登录后资产仍存在，并能看到源项目和版本。
3. 从资产库把场景和人物导入另一个项目，生成任务使用选定版本。
4. 人物自动注册可信人像，`processing` 时依赖视频只等待，`active` 后才提交上游。
5. 注册失败时不丢失人物资产，并可以单独重试注册。
6. 生成中与失败资产均能按分类找到；历史资产补录和重复回调不产生重复版本。

### 百集生产

1. 提交 3 集样本，验证编号、实体复用、资产归档、镜头连续性和声音交付。
2. 扩大到 10 集，验证断点续传、局部重试、积分结算和 Worker 重启恢复。
3. 扩大到 100 集，验证全链路总耗时、对象存储容量、队列吞吐、失败率和分集播放下载；与用户确认的 1 天以内生成目标比较。
4. 人为让单集、单镜头、白名单和合成任务失败，系统只重试对应条目，不重生成整部剧。
5. 重复点击批量生产或重复投递 Outbox，不重复扣费、不重复创建集数和任务。

## 9. 时长评估与实施顺序

当前没有百集全链路的实测证据。按 100 集乘 60 秒，共 6,000 秒成片；若平均每镜 10 秒，需要约 600 个视频任务。镜头数必须以实际分镜统计为准。

假设单账号实际并发为 3，每个任务占用槽位的平均时间分别为 1、2、3 分钟，在无重试、无其他任务争抢且依赖允许持续满载的理想条件下，仅视频阶段分别约 3 小时 20 分、6 小时 40 分、10 小时。这些是假设算例，不是 Provider 实测速度。

能否在 1 天以内完成取决于实际镜头数、耗时、重试率和有效并发。测量需包含长剧本调用、资产和加白、队列等待、视频生成、尾帧依赖、下载和合成；可并行部分按实际关键路径计算，避免把重叠时段重复相加。人工操作与等待单独记录，不能在没有说明的情况下从端到端耗时中扣除。

建议先跑 3 集闭环，再跑 10 集恢复/结算，最后按真实并发验证 100 集；独立统计人工操作时间和机器等待时间。会员通常 3 路、免费 1 路是现有摘要规则，组织实际额度还要受 Worker 与供应商限制；新增 B 端并发需独立配置并纳入预算。

实施顺序：先完成组织交付与积分守恒，再补自动资产归档及自动加白，然后接入长剧本、扩展批量编排，最后以带声音的百集交付做验收。现有任务价格、重复扣费防护、越权访问和未完成登录入口一并列入发布检查；支付占位页不能参与真实入账。

产品口径汇总：

| 项目             | 推荐默认值                                                 |
| ---------------- | ---------------------------------------------------------- |
| 百集单集时长     | 60 秒                                                      |

| 长剧本与分镜     | 接入另一项目已有后端与 API，耗时计入全链路                 |

## 11. 两个项目的整合范围

用户计划提供另一部分的 GitHub 仓库。该部分已有独立后端和 API，接入后需要联合审查两个项目，再决定部署和代码合并方式。本轮尚未读取另一仓库，不预设必须合并进程、数据库或框架。

整合目标是统一产品流程、明确数据与业务归属，并降低长期维护成本。账号交付、成员积分分配、自动资产库、人物自动加白、百集有声视频交付继续作为完整验收范围。

### 沿用现有生成链路的约束

- 另一项目的长剧本、分集及对应分镜结果通过适配层接入当前项目模型，保留原始 ID 与版本映射，并遵循现有草稿、保存和正式制作规则。
- 已有有效分镜映射为当前项目的镜头；缺少分镜时调用现有分镜能力，避免重复生成或覆盖已确认内容。
- 图片、可信人像和视频任务使用现有任务创建服务、队列、Worker、Provider 适配及结果写回机制，复用现有任务 ID、账本和审计关联。跨后端调用也必须纳入这一任务生命周期。
- 沿用当前组织鉴权、服务端定价、扣费/退款、并发及尾帧依赖规则；本需求要求的成员积分分配、自动归档、自动加白和缺陷修复在原模块内扩展并补回归验证。
- 保持分镜图非视频硬前置、按 Provider 能力取消、成片版本追踪等现有行为；新增批量入口与单任务入口走同一业务实现。
- 百集自动化负责持续调用已有能力、推进依赖和恢复失败任务；另一后端不得独立发起同一笔媒体生成、重复扣费或维护相冲突的任务终态。
- 现有编排存在的时长与镜头数上限在原模型中扩展；代码重构以职责清楚和消除实际重复为目的，保留已验证的业务行为。

### 接入后的审查与实施

1. 核对两个仓库的目标分支、未提交改动、技术栈、启动部署方式和现有测试，形成当前能力与重复实现清单。
2. 逐项确定账号/会话、组织权限、积分账本、项目/剧集、实体资产、任务、Provider 和媒体文件的唯一业务负责人及数据来源。
3. 对齐 API 契约、实体 ID、版本、错误码、鉴权和组织范围。跨服务调用保留用户及组织上下文，并校验授权，不能让一个后端仅凭请求传来的组织 ID 越权访问。
4. 建立剧本到分镜、资产到视频、任务到积分结算的明确交接。接口重试、回调重复或乱序、部分失败、用户切换组织、取消与服务重启均应有确定结果。
5. 结合代码选择复用模块或保留独立服务。统一重复的通用逻辑和业务规则，临时兼容代码明确替换路径；在迁移及调用方验证通过后移除旧实现。
6. 分阶段完成代码整合、数据迁移和回归。涉及迁移时保留已有数据映射与回退路径，不让两个后端长期各自维护一份可写的同类业务状态。
7. 用组织管理员建号、导出临时密码、分配积分、成员生成、失败退款、自动归档、自动加白和成片下载验证闭环，再进行百集产能验证。

### 可维护性验收

- 每个业务规则有明确的维护位置；价格、权限、任务状态和资产映射不在两个后端重复决策。
- 前端通过稳定的业务 API 使用功能，第三方密钥保留在服务端。
- 复用现有 contracts、Service、Repository 和队列机制；新增抽象必须解决实际重复或跨项目契约问题。
- 集成契约、组织隔离、积分守恒、任务幂等和恢复能力有针对性的自动化测试。
- 两个部分整合后的启动、配置、迁移、部署、回退和模块归属有同步文档。
- 只报告已验证的行为与产能；供应商配额、外部接口或缺失配置造成的限制明确列出。
