# 账号模型与后台文案

本文记录普通用户、个人账号、组织空间和管理后台之间的命名边界。这个边界是产品语义，不应被数据库兼容字段反向污染。

## 普通用户界面

- 普通个人用户不要看到“组织：个人”或“个人空间”作为主界面概念。
- 单一普通账号界面只显示“当前账号数据”。
- 只有用户加入多个企业或团队时，才显示“切换组织/空间”。
- 企业和团队才叫“组织空间”；个人账号不要叫“组织”。

## 管理后台

- 管理后台可以保留“个人账号”，因为运营确实需要按 C 端用户管理积分、状态、登录、资产和删除。
- “邀请普通成员”文案应简化为“邀请成员”，避免把账号范围和身份混在一起。
- 创建个人账号时，身份固定为 `member`；`admin`、`super_admin`、`owner` 属于平台内部系统账号。
- 创建或注册账号都应两次输入相同密码，并可切换是否显示密码。
- 删除账号需要两次确认；禁用和删除是不同操作。
- 改套餐、充值、删除、退出、刷新等后台按钮应有清晰 hover 提示。

## 后端兼容

- 后端继续保留 `organizationType: personal`，不要删除。
- `organizationType: personal` 是历史兼容和数据隔离结构，不是普通用户界面要强调的新产品概念。
- 个人账号仍需要底层组织/tenant 隔离能力，不能因为 UI 不显示“个人空间”就移除后端过滤。

## 判断准则

- 面向普通用户：用“当前账号数据”。
- 面向企业/团队：用“组织空间”。
- 面向管理员：用“个人账号”或“企业组织”。
- 面向数据库和兼容层：可以出现 `tenant`、`organizationType`、`personal`，但不要让它们决定前端文案。
