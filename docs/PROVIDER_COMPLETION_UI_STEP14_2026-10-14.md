## 新冻结合同

共享策略按任务事实识别 `kind=video` 且 `provider=seedance`。这类任务的新草稿固定包含 `provider-completed`，不因历史任务缺少回执、适配器名称或远端任务 ID 而省略。图片、本地 `local-compose` 和其他 Provider 不自动增加此项；这不代表这些类型已支持本回执。

服务端在组织/用户控制范围、项目、任务版本及已冻结状态校验后执行同一策略。省略 `provider-completed` 的新 Seedance 视频合同返回 HTTP 400 / `DELIVERY_PROVIDER_COMPLETION_REQUIRED`，要求重新审阅草稿；服务端不会悄悄增改用户确认过的合同。仅带兼容 ID `provider-accepted` 不能替代新冻结要求。

已有冻结合同的内容、哈希与判定规则保持原样，不追溯补入要求。旧合同明确要求 `provider-accepted` 时仍按第十三步的完成凭据语义核验；完全未纳入 Provider 要求的合同不会仅因缺少回执新增阻断，其他媒体、内容、物理及连续性门禁仍独立生效。

历史视频也可以冻结含新要求的合同，但缺少可信回执时该要求保持待补，不能凭任务完成状态、媒体 URL 或人工编辑 metadata 补造证明。本轮没有自动补签、迁移、付费重生成或绕过按钮。

冻结持久化另修复一个边界：PostgreSQL 生命周期条件写入若因损坏或不匹配的回执等原因返回空结果，接口必须报冲突并回滚，不能退回未持久化任务冒充冻结成功，也不能把该假成功镜像进缓存。正常无回执任务仍可冻结含完成要求的合同，随后等待可信证据。

## 回执说明

交付核验界面展示服务端当前证据快照中的 Provider 状态，区分通过、失败、待补和仅观察事实。判断使用 Provider 证据的最终 `status`，不能仅凭回执结构正确或 `completion.reason=verified` 显示通过：当前媒体读取失败、哈希不一致或暂时无法核验时，回执证据同样不能通过。

界面解释该回执证明服务端观察到远端完成并完成同次主视频入库，不等于上游数字签名，也不代表内容、物理或连续性质量验收通过。回执详情只展示供用户追溯的有限信息，不渲染存储路径、媒体版本原文或完整 metadata。合同是否纳入此要求单独标明，正式下载仍由服务端交付门禁决定。
