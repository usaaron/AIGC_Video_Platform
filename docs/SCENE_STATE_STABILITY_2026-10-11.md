# 状态表稳定性与复杂分镜请求：修正及四样本复测

2026-10-11。本轮修改已在 5183 所用的独立剧本后端启用。最终四个真实文字请求全部返回并保存到隔离测试库；三个简单样本通过本轮验收，复杂闸门样本仍未通过内容验收，候选采用被阻止。没有采用测试稿、修改正式正文或生成图片/视频。

## 1. 修正状态表的重复生成

原先模型同时写 initial、每次变化的 before/after，以及每镜 state_before/state_after，同一个事实会被多次改述。上一轮开门样本的动作顺序合理，但 before 与前次 after 措辞不同，因此整场被拦。

现在模型主要输出初始状态、变化后的值和逐字正文证据；程序从上一值推导省略的 before，再推导每镜状态。只有整条证据链通过引用、证据片段、顺序、唯一键检查后才回填。明确写出的矛盾值仍保留并阻止交付，不做同义词猜测或自动改剧情。

新增生成专用 Schema，省去上述派生字段和表演指导中可从状态表得到的身体状态、状态变化。保存和编辑 API 保留这些字段，旧稿继续可读。提示词要求一个状态项只表达一个维度，将门扇开合、锁定、人物位置、手部占用分开，避免固定的位置描述夹带过期持物信息。

## 2. 减少复杂请求的重复输出

没有延长超时、关闭思考或换模型。实际角色配置原本就是单请求及整场各 600 秒；此前约 300 秒的传输失败不能直接归因于本地时限。历史记录缺少底层原因，不能据此断言是哪一层断开。

本轮保留完整正文、引用顺序、动作过程、冲突与摄影规则，要求动作写在 action_sequence，表演字段仅补充必要信息，不逐镜机械复述所有字段。已知无歧义的字段归位之后，再清理模型回显的 `type: json_object` 标记，修复“列表嵌套与格式标记同时出现”时保存失败的问题。其他未知值、含内容字段和冲突副本继续拒绝。

复杂样本成功输出的 JSON（归位后、不含元数据、不含空白缩进）从前次 29,116 字符降至本轮首轮 16,497、最终 14,811 字符，约减少 43% / 49%。思考耗时仍占多数，不能把输出缩短直接解释为稳定完成率保证。

## 3. 同四份冻结正文的真实验证

模型：`deepseek-v4-1-flash-260910`，启用 high 思考。每例每轮一次真实请求；没有自动语义重写或换模型。两轮共 8 次真实调用，传输均完成；首轮开门因上述格式问题未保存，另做了一次零模型调用的原始响应回放，确认格式修正有效。回放不计作新生成或内容质量通过。

## 4. 仍然存在的通用缺口

复杂样本第一轮识别了核验门“逐人放行”与“仍锁着”的矛盾；第二轮识别了手部交接缺口，却把门的两个相反状态作为普通变化记录，未要求中间关锁动作的依据。这表明“每个状态都能引用原文”不等于“状态转变已经有充分因果证据”。第二轮也因此不能算复杂语义验收通过。

原文中的设施锚固、人群纵深、士兵制止和救援通路在生成动作里有呈现；这仅是文字检查，不是视频视觉验收。机械检查无报错也不等于任意持物、接触和空间语义均已自动验证。

时长口径须区分：这次输入的整集目标及剩余额度均为 105 秒（没有有效保留场次扣减），本场按权重分配的参考预算为 51 秒。最终本场 99 秒，后续仍需复核整集节奏，不能把 51 秒称为整集剩余额度，也不能把参考预算当成已经兑现。

下一项有针对性的改进应区分“状态陈述/观测”和“发生了变化的动作”：前后状态不同却没有变化依据时要求确认，不能直接作为合法变化。这需要通用合同与反例验证，不能用门锁关键词特判代替，也不应删除当前样本矛盾来制造全通过。
