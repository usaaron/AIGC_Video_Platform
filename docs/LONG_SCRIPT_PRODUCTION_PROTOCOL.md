# 序幕 TV 长剧本生产协议

版本：`xumu.production.v1`

本文档用于长剧本生成方与序幕 TV 的联调。请将本文档中的“必须”视为接口约束，而不是写作建议。

## 1. 目标

长剧本生成方可以生成约 40 万字甚至更长的小说正文，但序幕 TV 不能直接把整部小说一次性送入分镜或视频模型。

双方采用分层生产：

```text
小说正文
  -> 章节
  -> 章节摘要与事实
  -> 故事资产与世界观
  -> 分集大纲
  -> 剧情场次
  -> 可制作镜头
  -> 视频生成任务
```

长剧本生成方负责故事、人物、章节、分集和剧情场次；序幕 TV 负责将剧情场次编译成镜头、注入资产、计算镜头时长、处理尾帧衔接并进入视频生成队列。

**不要让一个模型在一次请求中同时生成 40 万字小说和全部最终镜头提示词。** 这会造成输出截断、编号丢失、上下文污染、重复剧情和镜头越写越空泛。

## 2. 对象关系

对象之间的关系必须保持如下结构：

```text
一个项目
  -> 一个原著版本
    -> 多个章节
  -> 多个分集
    -> 每集多个剧情场次
      -> 每场多个可制作镜头
        -> 每镜一个视频生成任务
```

### 2.1 术语定义

| 对象       | 含义                                                           | 是否直接交给视频模型   |
| ---------- | -------------------------------------------------------------- | ---------------------- |
| 原著版本   | 40 万字小说或长剧本文本，保持完整、可追溯、不可被改编结果覆盖  | 否                     |
| 章节       | 原著中的自然章节或平台切分块，保存原文偏移量                   | 否                     |
| 事实库     | 从章节中提取的人物、地点、物品、时间线、世界规则和伏笔         | 否                     |
| 分集       | 最终播出的第 1 集、第 2 集等，有明确时长和结尾钩子             | 否                     |
| 剧情场次   | 同一时间、地点和连续戏剧事件组成的场次，通常包含多个动作和对白 | 否，先交给序幕 TV 编译 |
| 可制作镜头 | 4 至 15 秒内可以实际执行的一段连续视频动作                     | 是                     |
| 视频任务   | 对一个可制作镜头的具体生成、重试和结果记录                     | 是                     |

**特别注意：剧情场次不等于视频镜头。**

例如：

```text
E01-S03 剧情场次：观景桥上的阻拦
  E01-S03-M01 岚星进入观景桥并发现异常，5 秒
  E01-S03-M02 守桥人横移挡路并索要凭证，5 秒
  E01-S03-M03 岚星亮出信物，守桥人态度变化，6 秒
  E01-S03-M04 恒星提前升起，所有人抬头，钩子，5 秒
```

序幕 TV 的界面可以提供“按场次生成”，但后台会把该场次下的多个镜头按顺序加入视频队列。

### 2.2 不允许的关系

- 一个剧情场次不能跨越两个分集。
- 一个可制作镜头不能跨越两个剧情场次。
- 不能让视频模型自行猜测镜头属于哪一集。
- 不能通过镜头正文中的“第几集”文字临时推断集号。
- 不能把整部小说重复发送给每一个分镜请求。

## 3. 编号规则

所有编号必须稳定、唯一、可重试。重新生成同一个对象时，编号不变，版本号增加。

```text
项目：PROJECT-001
原著版本：NOVEL-001-V01
章节：C001
分集：E001
剧情场次：E001-S001
可制作镜头：E001-S001-M001
```

推荐规则：

- `E001`：三位数字的分集编号。
- `E001-S001`：分集内的剧情场次编号。
- `E001-S001-M001`：场次内的可制作镜头编号。该编号由序幕 TV 生成方负责。
- `entityId`：人物、地点、物品和服装的稳定资产引用编号。
- `sourceChapterIds`：当前内容来源的章节编号列表。
- `sourceVersion`：原著版本。
- `adaptationVersion`：改编版本。
- `shotVersion`：镜头版本。

同一个人物不能因为在不同章节出现就生成多个实体。例如“岚星”“星主”“那个女孩”必须归并到同一个 `entityId`，并将其他称呼放在 `aliases` 中。

## 4. 双方职责

### 4.1 长剧本生成方负责

必须负责：

1. 保持原著正文的章节顺序和内容完整性。
2. 输出章节编号、标题、原文偏移量和来源关系。
3. 输出人物、地点、物品、服装和世界规则。
4. 输出分集目标、主要冲突、递进阻力和结尾钩子。
5. 输出剧情场次卡，而不是最终视频提示词。
6. 明确人物在场次开始和结束时的状态。
7. 将动作写成画面中能看见的动作和状态变化。
8. 将对白区分为对白、画外音、内心独白和现场音效。
9. 使用稳定的实体 ID 和分集/场次 ID。

### 4.2 序幕 TV 负责

必须负责：

1. 根据场次动作和时长编译可制作镜头。
2. 将剧情场次拆成 4 至 15 秒的视频镜头。
3. 计算动作密度、对白时长和镜头数量。
4. 将已确认的人物、场景、物品和服装资产注入镜头。
5. 生成构图、光影、运镜、负面约束和视频 Provider 提示词。
6. 将上一镜尾帧、人物位置、视线、物品状态和光线状态传给下一镜。
7. 处理单镜失败、重试、暂停、继续和版本回滚。
8. 将每个镜头独立加入视频生成队列。

长剧本生成方**不需要**生成 Provider 专用提示词，也不需要自行生成资产图片。它只需要给出可拍摄、可拆分、可追踪的剧情数据。

## 5. 分集规则

每集必须有独立的结构，不得只返回一段没有集号的连续正文。

每集至少包含：

- `episodeId`
- `title`
- `targetDurationSeconds`
- `sourceChapterIds`
- `openingState`
- `mainGoal`
- `mainConflict`
- `escalations`
- `turningPoint`
- `sceneCountTarget`
- `hook`
- `closingState`

推荐镜头预算，仅作为初始规划，最终由序幕 TV 校验：

| 单集时长 | 推荐剧情场次数 | 推荐可制作镜头数 |
| -------- | -------------: | ---------------: |
| 60 秒    |      2 至 4 场 |      10 至 16 镜 |
| 120 秒   |      4 至 7 场 |      18 至 30 镜 |
| 180 秒   |     6 至 10 场 |      30 至 45 镜 |
| 300 秒   |     8 至 14 场 |      40 至 65 镜 |

每集结尾必须有明确的钩子，例如：

- 新信息突然出现。
- 主角遭遇明显受辱或失败，但即将反击。
- 关键人物身份即将暴露。
- 重要物品即将被夺走或启动。
- 目标人物突然出现。
- 关系、规则或危险状态发生不可逆变化。

“气氛紧张”“观众期待后续”不能单独作为钩子，必须写出画面中真正发生的变化。

## 6. 剧情场次规则

剧情场次按照“时间、地点、连续事件和戏剧目标”切分，而不是按照字数或标点机械切分。

每个剧情场次必须包含：

- `sceneId`
- `episodeId`
- `sourceChapterIds`
- `locationId`
- `time`
- `characters`
- `goal`
- `obstacle`
- `turn`
- `entryState`
- `actions`
- `dialogue`
- `exitState`
- `hook`

### 6.1 动作要求

每个剧情场次至少包含 2 至 3 个可见动作或状态变化。动作不能只写：

```text
情绪升级、气氛紧张、两人对峙、主角很生气
```

必须改写为画面可执行内容，例如：

```text
岚星先停下脚步，视线越过守桥人的肩膀看向远方恒星。
守桥人横移一步挡住桥口，左手压住腰间的警铃。
岚星取出旧信物放到桥栏上，守桥人看清纹章后后退半步。
```

主要角色、配角和背景角色在场次中都应有符合场景的动作、视线或表情变化，但不要为了凑动作添加与剧情无关的随机行为。

### 6.2 状态要求

`entryState` 必须能够作为本场第一个镜头的起始状态。

`exitState` 必须能够作为本场最后一个镜头的结束状态，并明确：

- 人物位置。
- 人物朝向和视线。
- 人物手中或身边的关键物品。
- 服装、伤势或外观变化。
- 场景中的光线、天气或环境状态。
- 下一场需要承接的事实。

## 7. 推荐交付格式：JSONL

不要返回一个包含整部 40 万字内容的巨大 JSON 数组。推荐使用 JSONL：每一行一个完整记录，可以流式写入、断点续传和单条重试。

推荐交付包：

```text
production-package/
  manifest.json
  novel.txt
  chapters.jsonl
  entities.jsonl
  episodes.jsonl
  scenes.jsonl
  README.md
```

### 7.1 manifest.json

```json
{
  "schemaVersion": "xumu.production.v1",
  "projectId": "PROJECT-001",
  "novelId": "NOVEL-001",
  "sourceVersion": "NOVEL-001-V01",
  "title": "天穹回想",
  "language": "zh-CN",
  "contentType": "web-series",
  "visualStyle": "CG",
  "chapterCount": 120,
  "episodeCount": 80,
  "files": {
    "novel": "novel.txt",
    "chapters": "chapters.jsonl",
    "entities": "entities.jsonl",
    "episodes": "episodes.jsonl",
    "scenes": "scenes.jsonl"
  }
}
```

### 7.2 chapters.jsonl

```json
{
  "schemaVersion": "xumu.production.v1",
  "recordType": "chapter",
  "chapterId": "C001",
  "order": 1,
  "title": "观星桥",
  "startOffset": 0,
  "endOffset": 6234,
  "sourceChapterTitle": "第一章 观星桥",
  "summary": "岚星在观景桥发现恒星提前升起。",
  "previousChapterId": null,
  "nextChapterId": "C002"
}
```

章节可以由原著真实章节组成，也可以是平台按约 4,000 至 8,000 个中文字符切分出的处理块。切分时必须保持句子、对白和事件完整，并保存原文偏移量。

### 7.3 entities.jsonl

```json
{"schemaVersion":"xumu.production.v1","recordType":"entity","entityId":"CHAR-001","kind":"character","displayName":"岚星","aliases":["星主","那个女孩"],"description":"确认过的角色基础信息","firstEpisodeId":"E001","attributes":{"gender":"女","age":"青年","role":"主角"},"assetHints":["固定发型","左肩旧披风"]}
{"schemaVersion":"xumu.production.v1","recordType":"entity","entityId":"LOC-001","kind":"scene","displayName":"观景桥","aliases":["观星桥"],"description":"悬在云海上的旧观景桥","attributes":{"space":"exterior","era":"ancient","time":"night"}}
{"schemaVersion":"xumu.production.v1","recordType":"entity","entityId":"PROP-001","kind":"prop","displayName":"旧信物","aliases":["银色信物"],"description":"带有天穹环城纹章的金属信物"}
```

允许的 `kind`：

```text
character
scene
prop
costume
animal
```

人物、地点、物品和服装必须尽量复用已有实体，不要在每个场次中重新创造同义名称。

### 7.4 episodes.jsonl

```json
{
  "schemaVersion": "xumu.production.v1",
  "recordType": "episode",
  "episodeId": "E001",
  "order": 1,
  "title": "提前升起的恒星",
  "targetDurationSeconds": 120,
  "sourceChapterIds": ["C001", "C002"],
  "openingState": "岚星从云雾中进入观景桥，远方恒星尚未升起。",
  "mainGoal": "确认恒星为何提前升起。",
  "mainConflict": "守桥人封锁桥面，不允许任何人接近观星台。",
  "escalations": ["守桥人启动警铃", "恒星提前升起并照亮信物纹章"],
  "turningPoint": "守桥人认出岚星手中的旧信物。",
  "sceneCountTarget": 5,
  "shotCountTarget": 24,
  "hook": "恒星光芒照出岚星手腕上的第二道纹章。",
  "closingState": "岚星身份即将暴露，守桥人准备关闭整座观景桥。",
  "sceneIds": ["E001-S001", "E001-S002", "E001-S003", "E001-S004", "E001-S005"]
}
```

### 7.5 scenes.jsonl

下面是一条完整的剧情场次记录。`actions` 是剧情场次中的可见动作，序幕 TV 会进一步编译成 `M001`、`M002` 等可制作镜头。

```json
{
  "schemaVersion": "xumu.production.v1",
  "recordType": "scene",
  "episodeId": "E001",
  "sceneId": "E001-S001",
  "order": 1,
  "sourceChapterIds": ["C001"],
  "locationId": "LOC-001",
  "time": "夜",
  "weather": "雾",
  "characters": [
    { "entityId": "CHAR-001", "displayName": "岚星", "role": "主角" },
    { "entityId": "CHAR-002", "displayName": "守桥人", "role": "配角" }
  ],
  "goal": "岚星确认远方恒星是否已经提前升起。",
  "obstacle": "守桥人横在桥口，拒绝让岚星靠近观星台。",
  "turn": "守桥人认出岚星展示的旧信物，态度从阻拦变为恐惧。",
  "entryState": "岚星从画面左侧的云雾中进入，右手握住旧信物；守桥人站在桥口右侧，左手压住腰间警铃。",
  "actions": [
    {
      "actionId": "A01",
      "text": "岚星停下脚步，抬眼越过守桥人的肩膀观察远方恒星。",
      "visibleChange": "岚星由行走变为停立，视线从守桥人转向远方。"
    },
    {
      "actionId": "A02",
      "text": "守桥人横移一步挡住桥口，右手抬起示意岚星退后。",
      "visibleChange": "桥口被完全遮挡，守桥人身体朝向岚星。"
    },
    {
      "actionId": "A03",
      "text": "岚星将旧信物放在桥栏上，守桥人看清纹章后后退半步并松开警铃。",
      "visibleChange": "信物进入画面中心，守桥人表情和站位发生明显变化。"
    }
  ],
  "dialogue": [
    {
      "type": "dialogue",
      "speakerEntityId": "CHAR-002",
      "speaker": "守桥人",

    },
    {
      "type": "innerVoice",
      "speakerEntityId": "CHAR-001",
      "speaker": "岚星",
      "text": "它比预言提前了整整一夜。"
    }
  ],
  "audioCues": ["雾中风声", "金属信物放在桥栏上的轻响", "远处低沉的钟声"],
  "exitState": "岚星站在桥口左侧，旧信物位于桥栏中央；守桥人退到右侧，目光从信物移向岚星。",
  "hook": false,
  "productionHints": { "priority": "dialogue-and-reaction", "estimatedDurationSeconds": 16 }
}
```

### 7.6 对白类型

`dialogue.type` 只能使用以下值：

```text
dialogue       角色现场对白
voiceOver      画外音
innerVoice     内心独白
sound          现场声音或音效
```

对白必须短、明确并推动冲突。没有对白时，不要返回空字符串，应返回有效的动作、表情、现场声音或内心独白。

## 8. 直接兼容旧版文本格式

如果暂时无法输出 JSONL，可以输出一行一个剧情场次，使用以下格式。字段名、分隔符和编号必须稳定：

```text
集：E001｜场次：E001-S001｜剧情：岚星进入观景桥并确认恒星提前升起。｜目标：确认恒星异常升起的原因。｜阻力：守桥人封锁桥口并拒绝放行。｜变化：守桥人认出旧信物后退并产生恐惧。｜场景：观景桥，夜，雾。｜角色：岚星、守桥人。｜入场状态：岚星从左侧云雾中进入，右手握住旧信物；守桥人站在右侧压住警铃。｜动作：动作1：岚星停下并观察远方恒星；动作2：守桥人横移挡住桥口并抬手阻拦；动作3：岚星将旧信物放在桥栏上，守桥人看清纹章后退半步。｜对白：[对白]守桥人：今夜封桥，任何人不得靠近。 [内心独白]岚星：它比预言提前了整整一夜。｜出场状态：岚星站在桥口左侧，信物位于桥栏中央；守桥人退到右侧并重新看向岚星。｜风格：沿用项目视觉风格。｜构图：岚星位于左侧，守桥人位于右侧，桥栏和恒星位于中远景。｜光影：雾中冷色月光从后方照亮信物边缘。｜运镜：从桥口中景缓慢推进到信物和守桥人的反应。｜衔接：下一镜从信物位于桥栏中央的状态开始。｜钩子：否
```

JSONL 是首选格式。旧版文本格式只作为过渡兼容，不作为长期协议。

## 9. 批量生成和断点续传

40 万字内容必须分阶段、分批次处理，不能由单个请求承担全部工作。

推荐批处理方式：

| 阶段       | 一批处理范围                   | 失败处理             |
| ---------- | ------------------------------ | -------------------- |
| 原著导入   | 章节或 4,000 至 8,000 字处理块 | 只重试当前章节/块    |
| 章节摘要   | 4 至 8 个章节                  | 只重试失败章节       |
| 事实库     | 10 至 30 个摘要                | 重新生成当前事实版本 |
| 分集大纲   | 1 至 3 集                      | 只重试失败分集       |
| 剧情场次   | 1 集或 4 至 8 场               | 只重试失败场次       |
| 可制作镜头 | 序幕 TV 后台按集排队           | 只重试失败镜头       |

每个批次必须支持：

- `idempotencyKey`，重复提交不能产生重复分集或场次。
- `sourceVersion`，明确使用哪一版原著。
- `adaptationVersion`，明确使用哪一版改编方案。
- `status`：`queued`、`running`、`completed`、`failed`、`paused`、`cancelled`。
- `completedItemIds` 和 `failedItemIds`。
- 单条错误信息，不要因为一条失败使整部作品回滚。
- 断点续传，不要要求从第一章重新开始。

推荐的提交顺序：

```text
先提交 manifest 和章节
  -> 提交 entities
  -> 提交 episodes
  -> 提交 scenes
  -> 序幕 TV 校验关系
  -> 用户确认某一集
  -> 序幕 TV 编译镜头并生成
```

如果分集和场次是边生成边返回的，也必须保证同一集的 `episode` 记录先于其 `scene` 记录，或者在记录中提供完整的 ID 引用，平台会等待依赖完成后再处理。

## 10. 序幕 TV 的分镜输入

序幕 TV 生成一个可制作镜头时，使用以下上下文，而不是使用整部小说：

```text
项目视觉风格
已确认资产及资产版本
当前分集大纲
当前剧情场次
当前场次的入场状态
当前动作及对白
上一镜出场状态和尾帧
下一动作的目标
下一场的开场状态
```

镜头编译器会补齐或计算：

- 镜头编号。
- 镜头时长。
- 构图和人物位置。
- 光影和色温连续性。
- 运镜方式和结束位置。
- 负面提示词。
- 资产快捷引用。
- 尾帧传递。
- 视频 Provider 参数。

合作方不要为了“看起来像分镜”而凭空添加不属于故事的摄像机动作、人物、道具或场景。

## 11. 强制质量校验

提交前必须通过以下检查：

### 11.1 结构检查

- 所有 `episodeId` 唯一且连续。
- 所有 `sceneId` 唯一，并且引用存在的 `episodeId`。
- 所有 `entityId` 唯一，别名不能导致重复实体。
- 每个场次只属于一个分集。
- `sourceChapterIds` 必须引用存在的章节。
- 所有 JSONL 行必须是独立合法 JSON。

### 11.2 内容检查

- 每场至少有 2 至 3 个可见动作或状态变化。
- 每场有目标、阻力和变化。
- 每场有入场状态和出场状态。
- 重要配角和背景角色不能在所有镜头中保持完全静止。
- 每个动作必须能被摄像机拍到。
- 台词必须标明对白、画外音或内心独白。
- 每集最后一个场次必须包含钩子或不可逆状态变化。
- 不得用“情绪升级”“气氛紧张”等抽象词替代行为。
- 不得在当前场次提前执行下一场的关键事件。
- 不得重复描述上一镜已经完成的动作。

### 11.3 时长检查

- 单个可制作镜头目标时长为 4 至 15 秒。
- 一个镜头不要塞入多个互不连续的地点变化。
- 一句对白的长度必须允许角色在镜头时长内说完。
- 多个动作必须按先后顺序排列，不能只罗列动作名。
- 超过单镜可执行范围的动作必须交给序幕 TV 拆成多个镜头。

## 12. 推荐给长剧本 Agent 的系统指令

下面的内容可以直接作为长剧本生成 Agent 的生产约束：

```text
你是负责长篇故事和影视改编结构的编剧，不是最终视频提示词生成器。

你可以生成小说正文，但必须同时维护可追踪的章节、实体、分集和剧情场次结构。小说正文是原著版本，剧情场次是改编版本，两者不能互相覆盖。

请严格遵守 xumu.production.v1：

1. 所有内容必须带有稳定的 projectId、sourceVersion、episodeId、sceneId 和 entityId。
2. 一个剧情场次只能属于一个分集；一个分集可以包含多个章节；一个章节也可以跨越相邻分集，但必须记录 sourceChapterIds。
3. 剧情场次不是最终视频镜头。你只输出可拍摄的剧情场次，序幕 TV 会进一步拆成 4 至 15 秒的可制作镜头。
4. 每个剧情场次必须有目标、阻力、变化、入场状态、至少 2 至 3 个可见动作、对白或有效现场声音、出场状态。
5. 动作必须写成人物、配角或环境实际发生的动作、表情、视线、姿态、位置、物品状态或光线变化。禁止只写“情绪升级”“气氛紧张”“两人对峙”。
6. 对白必须明确类型：dialogue、voiceOver、innerVoice 或 sound。没有台词时，必须写有效动作、反应或现场声音，不能返回空白。
7. 每集结尾必须有可见的悬念、失败、身份暴露、危险升级、关系改变或新的不可逆状态。
8. 不要凭空添加原故事没有的主要人物、关键道具、地点或世界规则。已有实体必须复用 entityId，并把新称呼写入 aliases。
9. 使用 JSONL，一行一个独立记录。不要返回巨型 JSON 数组，不要在 JSONL 中混入解释、Markdown 或代码围栏。
10. 如果某条记录无法生成，返回该记录的 failed 状态和错误信息，不要伪造空内容，不要让整个作品从头重生成。

序幕 TV 会负责镜头编号、镜头时长、构图、光影、运镜、资产提示词、负面提示词、尾帧衔接和视频 Provider 参数。不要在场次中输出 Provider 专用参数。
```

## 13. 最终验收标准

长剧本生成方完成联调后，必须能够交付以下结果：

1. 一部 40 万字原著正文，章节顺序和原文可追溯。
2. 一份实体清单，人物、地点、物品和服装没有明显重复。
3. 一份分集清单，每集有时长、目标、冲突和结尾钩子。
4. 一份剧情场次 JSONL，每场有稳定编号和完整状态变化。
5. 任意选择一集后，序幕 TV 可以只读取该集相关数据完成分镜。
6. 任意一个场次失败后，只重试该场次，不重写全书。
7. 任意一个镜头失败后，只重试该镜头，不重生成整个场次。
8. 同一份数据重复提交不会产生重复章节、分集、场次或任务。

联调的第一批建议使用 2 至 3 集、每集 60 至 120 秒的小样本。先验证编号、关系、动作密度、出入场状态和钩子，再批量处理完整 40 万字内容。
