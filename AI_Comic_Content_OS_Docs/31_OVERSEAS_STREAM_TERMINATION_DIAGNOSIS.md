# 海外流式终止诊断与修复

日期：2026-09-07（UTC）。范围：第 4 步三集验收失败后的传输诊断。当前仍未通过三集正文验收。

## 已确认的问题与修复

本地故障注入确认，`RealLLMAdapter._stream_text()` 看到 `[DONE]` 后仍继续读取；Responses 的完成、失败和未完成事件也只记录状态，没有停止读取。供应商已经发送终止标记但仍保持连接时，调用会继续等待 socket 结束。

适配器现在在终止事件处停止读取并关闭响应，先保留事件中的 usage 和 response ID。Chat 的 `finish_reason` 后可能还有独立 usage chunk，因此继续读到 `[DONE]`；不会因提前退出而丢掉尾部用量。

同时修复另一处错误：明确 `failed`、`incomplete` 或 `cancelled` 的流即使留下可解析 JSON，也不能成为成功结构化输出。现在保留原文与终止原因，抛出结构化输出错误，且不会进入后续 schema 修复请求；流式路由日志也不再标成成功。

这证明代码存在可复现的终止缺陷，但不能确定它就是上一轮 900 秒未完成请求的根因。第 30 号报告保存的原日志没有终止事件或逐阶段时点，无法补回缺失证据。

响应头、首个响应体字节可能来自 SSE 元数据或心跳，并不等于正文开始。首次文字回调受适配器批量刷新影响，也不是逐 token 的精确到达时点。单次小 JSON 的时延不代表长正文时延。

真实诊断还发现探针统计缺陷：消费者正常在终止事件处退出时，Python 通过 `GeneratorExit` 关闭迭代器，meter 的 `except BaseException` 将其记录为 `outcome=error`。因此原始 `summary.json` 同时保留应用层 `response_verified` 和传输统计 `error_type=GeneratorExit`；不能把后者当成供应商生成失败，也不能把原文件改写成全链路统计通过。

随后修正 meter：迭代器正常退出不记传输错误，由响应 `close()` 记录关闭结果；真实读取异常仍保留原错误。以真实适配器和本地假传输覆盖 Responses、Chat 两条路径，确认只请求一次、终止后不再读取、底层关闭一次、usage 保留、最终统计为 `closed` 且只落盘一次。此修正没有再次调用真实模型，故真实目录的源码指纹对应修正前的 meter。

## 剩余边界与下一步

本次修复只保证收到明确终止事件后停止读取。生产适配器仍未设置累计请求时长上限：持续心跳且始终没有终止事件时，socket 操作超时不能阻止整次调用持续过长。测试探针的进程 watchdog 可限制测试总时长，不能代替生产中的累计截止和任务回收。

适配器也仍沿用兼容策略：干净 EOF、没有终止事件但 JSON 可解析时允许继续校验。本轮没有将此兼容行为改成强制拒收，因此不能声称所有异常结束均已被拦截。

下一步是在新隔离目录按既有最多 6 次请求、900 秒总时限复测三集，观察初稿、编辑和失败恢复各阶段，按第 29 号报告审核语义和账本继承。此步骤通过后再进入八集单元验收；身份认证、多租户、统一金额预算、生产请求截止及无人值守运行仍待完成。六步方案仍剩第 4、5、6 步，共 3 步。
