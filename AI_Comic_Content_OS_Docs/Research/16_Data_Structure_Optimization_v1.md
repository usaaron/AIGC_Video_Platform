# My Comic 数据结构优化报告 v1

## 1. 优化目标

本次优化的目标不是引入更多数据结构，而是在长篇剧本持续生成时同时控制三件事：

1. 连续性状态不能丢失、重复或被错误覆盖。
2. 角色和集数增加后，同步和检索成本不能按无必要的平方级增长。
3. 下一集收到的记忆必须是完整的记录，不能因为字符数截断而得到半条状态。

原则是“质量和效率优先，数据结构服从问题”。只实现有明确收益的结构，不为技术复杂度而复杂化。

## 2. 当前工作流的结构

当前项目实际上已经形成了以下几层：

```text
固定人物设定 / Story Bible
        ↓
递归剧情树 + 分集路线图
        ↓
单集正文
        ↓
人物状态、剧情线、Hook、世界状态变化
        ↓
下一集的连续性记忆包
```

其中“完整历史”保存在已生成分集正文及其结构化字段中，“当前状态”保存在项目工作区中。下一集不读取整部正文，而读取当前状态和与本集相关的约束。

## 3. 本次已经落地的优化

### 3.1 人物名称使用 Map 索引

旧逻辑在每个生成角色、人物状态更新中反复遍历全部角色查找同名人物。现在使用：

```text
normalized_character_name → CharacterDraft
```

人物状态更新、模型补充人物资料和回退状态都使用常数时间查找。固定设定仍然优先，模型只能补充空字段。

### 3.2 关系和人物证据改为“一次扫描，多个结果”

旧逻辑大致是：

```text
每一对人物 → 扫描所有集 → 扫描所有场景 → 查找两人是否同时出现
```

角色较少时不明显，但角色和集数增长后会接近：

```text
O(角色数² × 集数 × 场景数)
```

现在先按集和场景建立证据索引：

```text
人物 ID → 各集最后一次有效证据
关系 ID → 各集第一次有效关系证据
```

同一场景中先得到出现的人物集合，再只生成实际共同出现的人物对。这样复杂度更接近：

```text
O(集数 × 场景数 × 人物数 + 实际共同出现的人物对)
```

这不会改变关系判断规则，只减少重复读取和重复字符串扫描。

### 3.3 世界状态使用复合键和去重集合

世界状态使用：

```text
entity_key + state_domain → 当前状态
```

例如：

```text
item.access_card_001 + condition
character.linxia + life
location.old_hospital + access
```

历史变化仍然追加，但用“集数 + 转换类型 + 当前状态”组成签名，重建或刷新时不会重复追加同一条历史。原先需要扫描整段历史判断重复，现在使用 Set 直接判断。

### 3.4 连续性记忆包按完整记录装箱

旧逻辑先把所有内容拼成一个大字符串，最后按字符数截断。这可能造成：

```text
物品状态：门禁卡芯片被烧毁；后续硬约束：原门禁卡不能再
```

现在按完整记录装箱，分别为以下区域分配预算：

```text
世界硬状态       1700 字符
人物连续性       3300 字符
剧情线           1000 字符
追看点            500 字符
人物关系          500 字符
```

每一条记录要么完整进入，要么不进入；只有单条记录本身异常过长时才进行局部压缩。

### 3.5 不可逆状态提高优先级

世界状态排序现在优先保留：

- 死亡和存在状态
- 永久伤残、健康和行动能力
- 物品丢失、毁坏、所有权和持有状态
- 地点封锁和法律限制
- 带有明确后续硬约束的状态

普通、临时、近期状态仍会进入记忆包，但不会挤掉更重要的硬约束。

## 4. 当前推荐的数据结构组合

不是所有内容都使用同一种结构，而是按问题选择：

| 问题 | 合适结构 | 原因 |
|---|---|---|
| 当前人物状态 | Map | 通过人物 ID 快速读取最新状态 |
| 历史状态变化 | 追加式数组/事件列表 | 保留原因、集数和场景证据 |
| 人物认知 | 人物 ID + fact ID 的嵌套 Map | 不把一个人的秘密传给另一个人 |
| 剧情拆分 | 树 | 表达篇章、阶段、剧情段和叶节点的父子关系 |
| 分集执行 | 有序列表 + 任务状态 | 支持逐集生成、失败重试和断点继续 |
| 关系 | 关系 ID Map + 关系变化列表 | 支持当前关系和历史变化 |
| Hook/伏笔 | 未兑现事项列表 | 能跟踪设置、推进和兑现状态 |
| 连续性约束 | Set/Map | 快速判断死亡、毁坏、封锁等硬条件 |
| 记忆检索 | 稳定 ID、别名索引、全文检索 | 解决代称和表达变化，不依赖单一关键词 |

## 5. 暂不引入的方案

### 5.1 每个角色一个物理数据库

不采用。跨人物事件、共享物品、共同地点和关系会产生重复数据，增加迁移、备份和一致性成本。使用同一个数据库中的 `project_id + character_id` 已经能够实现逻辑隔离。

### 5.2 纯关键词字典

不采用为唯一方案。关键词无法可靠覆盖昵称、代称、同义表达和间接叙述。稳定 ID 和别名索引负责精确命中，全文或语义检索只作为后备。

### 5.3 立即建设完整知识图谱或向量数据库

暂不采用。当前主要瓶颈是结构化状态组织和上下文选择，而不是语义搜索能力。过早加入会增加部署、调试和成本，且不能自动解决模型写出矛盾剧情的问题。

## 6. 版本化连续性账本已接入

当前已经实现：

```text
当前批次中的即时结构化状态
        +
最近一次作者确认的后端检查点
        ↓
下一集生成上下文
```

具体规则如下：

1. 只有草稿确认、修订稿或终稿工件成功保存后，才提交新的 `ContinuityLedger` 版本；生成失败和未确认正文不会污染长期记忆。
2. 人物生存、伤病、行动能力、认知、位置、性格变化，物品和环境状态，剧情线、关系、Hook 和最近剧情结果均可进入账本。
3. 每条世界状态保留变化原因、发生集数和场景证据，不只保存结论。
4. 人物认知使用稳定 `knowledge_key` 合并，而不是通过未来文本关键词猜测。
5. 实体名称建立别名索引；同类型、同名称的实体即使模型换了 `entity_key`，仍归一到原稳定实体。
6. 第一次为旧项目建立账本时，系统按集回放已有工件，并按“终稿 > 修订稿 > 草稿”选择每集最高阶段版本。
7. 较早单集的迟到重试不会把已经推进到更后集的检查点倒退。
8. 生成上下文中的确认检查点限制在约 6900 字符，并优先保留死亡、毁坏、伤病、能力、持有、访问和法律状态等硬约束。

## 7. 当前仍然存在的边界

1. 前端仍会从已有分集重建当前批次的即时状态，这是为了支持未确认分集继续生成；后端账本只代表作者已经确认的可靠回退点。
2. 结构化校验可以保证字段、版本和证据完整，但还不能仅靠规则理解所有自然语言矛盾。
3. 已推进到后续集后再实质修改较早分集，目前不会自动重算所有后续正文；系统只阻止账本倒退。完整能力需要显式创建“从第 N 集重新生成后续”的分支工作流。
4. “不知道某事却做出知情决策”“伤病能力与动作冲突”等语义级问题，仍需要生成后连续性 QC。
5. 当前未引入向量数据库。稳定 ID、别名和结构化当前状态足以覆盖高风险连续性；只有长篇运行数据证明召回不足时才增加语义检索。

## 8. 下一阶段建议

下一步最值得做的是增加生成后检查：

- 死亡人物是否再次进行时间线内行动
- 已毁坏或转移的物品是否被旧持有人继续使用
- 当前行动能力是否允许本集动作
- 人物的知识状态是否允许当前决策
- 位置、封锁、天气、法律和社会环境是否被违反

检查不应直接修改正文，而应给出矛盾类型、冲突状态、证据集数和建议处理方式；用户可以重试本集或接受有明确剧情解释的状态变化。

只有当实际运行数据显示精确索引和别名命中率不足时，再增加全文或语义检索。
