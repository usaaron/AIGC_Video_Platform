# 全流程架构审查

审查视角：专业编剧 + AI 全栈工程。审查对象为当前工作区代码、前置规划 Prompt、正文生成链路、前端状态和既有真实/Mock 验收记录。

## 结论

整体方向合理：先锁定 Story Bible，再递归拆分剧情树、分集规划、正文生成，并保留版本和连续性。但当前流程仍存在“上游看起来完整、下游重新猜剧情”的结构性风险。最优先的修改不是增加更多模型调用，而是让每一层只承担一种责任，并让正文入口只接收已经完成的执行规格。

## P0/P1 问题

### P0：真实 Qwen 规划链路仍不可用

当前配置的 Qwen 网关在真实测试中发生 TLS EOF，公共 DNS 还返回 NXDOMAIN。分集规划无法完成时，后续正文、保存读回和全流程验收都没有真实证据。这个问题属于外部配置/网络链路，但在恢复前不能宣称中文完整链路通过。

### P1：缺少场景蓝图仍会被服务端补成“完整”

`StoryPlanningService._ensure_episode_item_short_drama_fields` 会在分集计划缺少 `scene_execution_plan` 时调用 `_fallback_episode_scene_execution_plan`，并把通用阶段字段替换成中央冲突、退出状态或悬念。这样生成结果能通过 Pydantic，却没有强模型真正做过逐场设计。

这与当前 Prompt 已要求强模型返回执行蓝图相冲突。正确行为应是：缺少蓝图时触发一次强规划模型的有界补全；补全后再检查；仍不完整才停在 `review_required`。不能由程序用模板文字替代编剧判断。

### P1：正文接口仍允许绕过前置规划

`ScriptGenerationDraftRequest.episode_context` 和 `EpisodeGenerationContext.approved_episode_plan` 都是可选字段。直接调用正文接口时，系统可以在没有批准分集计划、场景蓝图或完整连续性包的情况下组装 Prompt。

生产路径必须在正文模型请求之前检查：批准分集计划、逐场执行蓝图、连续性来源和当前版本指纹。缺失时先进入强规划补全；补全失败则零正文模型请求并返回明确状态。

### P1：快速正文模型还不是实际的策略边界

项目文档已经定义“强模型负责规划、快速模型负责执行”，但 `GenerationStrategy` 尚未把模型等级和前置准入真正绑定。当前 Prompt 虽然要求正文模型不要重新规划，系统却没有阻止未成熟计划进入正文。

应增加策略级 `strong_planner` / `fast_executor` 语义。`fast_executor` 只能接收 `execution_ready` 的计划；强模型也不能静默越过缺口，而是负责一次有界补全。

## P2 问题

### P2：场景执行字段仍不足以表达制作因果

已增加 `opposition`、`information_shift`、`choice_or_cost`、`evidence_requirements` 和 `forbidden_changes`，但这些字段目前仍为可选，且没有统一的确定性完整性检查。没有检查就无法证明“快速模型只是在执行”。

### P2：质量验收仍有一部分是 shadow 信号

README 明确 Story QC 和 Acceptance 仍不阻断 Finalization。这样结构和连续性问题可能被记录为报告，却仍被标成终稿。应把事实冲突、场景无结果、未批准关键事实和保存恢复失败设为阻断；语言重复和节奏偏差可以保留为警告。

### P2：连续性存在前后端多份投影

后端有 `ContinuityLedger`、生成上下文和记忆包，前端又有 `continuity.ts`、`episode-planning-memory.ts` 和本地项目状态。它们的职责目前大体区分，但还缺少一个明确的权威来源和版本指纹协议。否则前端显示的状态可能与正文 Prompt 注入的状态不同。

### P2：Liblib 方案后半段仍是设计，不是能力

[44_PREPRODUCTION_STORYBOARD_PLAN.md](44_PREPRODUCTION_STORYBOARD_PLAN.md) 已完整吸收了分镜、资产设计、图片/视频提示词和前期制作包的方案，但文档明确这些对象尚未进入运行代码。现有 Asset 模块更接近知识资产检索，不能当作项目级版本化 Asset Bible；分镜、PromptPack、PreflightQC、GenerationBrief 和不可变前期包都还没有完整实现。

## 编剧角度的流程判断

当前“输入 → Bible → 剧情树 → 分集计划 → 正文”的顺序正确，但要避免四种错误：

- Story Bible 写成百科全书，却没有人物的行为逻辑和误判方式；
- 剧情树写成事件列表，却没有每个节点独有的选择和代价；
- 分集计划写成摘要，却没有逐场的阻力、信息差和结果；
- 正文模型为了填字数、镜头和对白数量，重新发明事件。

因此分集规划是整个系统的关键编译层。它必须把上层故事编译成“演员和导演可以执行的场面指令”，而不是继续向正文传递抽象叙事词。

## 推荐修改顺序

1. 先修正 Qwen 配置并完成真实规划链路验证。
2. 重写分集规划 Prompt，使强模型一次返回完整逐场蓝图；缺失时只允许一次强模型补全。
3. 移除新流程的模板 fallback；缺失蓝图不保存为可批准计划。
4. 在正文入口增加 `execution_ready` 检查和零请求阻断。
5. 将快速/强模型等级绑定到策略和配置，而不是由调用方临时决定。
6. 统一连续性执行包的后端权威来源，前端只展示和编辑版本化结果。
7. 再实现 Liblib 方案的分镜、资产、PromptPack、PreflightQC 和交付包。

## 验收标准

- 强规划模型一次返回完整分集执行规格的比例可统计；
- 缺字段时最多一次自动补全，不产生模板化假蓝图；
- 没有 `execution_ready` 时正文请求数为 0；
- 同一批准计划交给强模型和快速模型，事实、场景结果和人物选择一致；
- 人工修改主要是语言和表演细节，而不是重新设计剧情；
- 真实 Qwen 规划、正文、保存、读回和恢复链路全部有证据；
- Liblib 方案只有在分镜和前期制作包真正进入运行代码后，才标记为已适配。
