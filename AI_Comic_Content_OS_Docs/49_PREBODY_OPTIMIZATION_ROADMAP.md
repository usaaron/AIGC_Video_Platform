# 正文前置链路优化方案

## 目标

把正文前的规划链路做成一套稳定的“执行规格生产线”，使较快、能力较弱的正文模型只负责把批准的逐场设计扩写为可拍正文。前置链路负责决定事实、因果、人物选择、场面机制和连续性；正文模型不再承担这些决定。

## 当前整体判断

项目现在已经具备故事圣经、递归剧情树、分集规划、场景执行蓝图和连续性记忆，但这些产物的责任边界还没有完全锁定：

- Story Bible 仍可能同时承担人物设定、剧情展开和集数分配；
- 剧情树已有递归和集数门禁，但对“每个节点独有的戏剧机制”和禁止快捷解决方式约束不足；
- 分集规划已有 `scene_execution_plan`，但场景模型没有把阻力、信息变化、代价和禁止改写项作为明确执行字段；
- `episode_roadmap_quality_issues` 目前主要检查场景计划缺失、进出状态重复和抽象字段重复，不能证明规划已经适合弱模型执行；
- 正文 Prompt 已要求“不要重新规划”，但生成入口还没有根据规划成熟度选择强模型或快速模型；
- 当前处于纯开发阶段，旧项目允许按新合同重新生成或迁移，不再为了旧数据保留会掩盖缺口的自动补全分支。

因此，首要任务不是增加更多摘要字段，而是建立一条明确的准入链：

```text
输入评估
  -> 故事圣经批准
  -> 剧情树节点批准
  -> 分集逐场执行规格
  -> 连续性执行包
  -> 快速正文模型准入
  -> 正文生成与三轮 QC
```

## 已确认的正文放行缺口

以下位置目前会让不完整的前置结果继续向正文流动，必须作为 P0 处理：

1. `ScriptGenerationDraftRequest.episode_context` 可为空，API 层没有强制要求批准的单集计划；直接调用正文接口可以绕过规划阶段。
2. `EpisodeGenerationContext.approved_episode_plan` 可为空，正文服务因此可以在没有批准路线图的情况下继续组装 Prompt。
3. `EpisodePlanGenerationItem.scene_execution_plan` 默认是空数组，模型没有返回逐场蓝图时，Pydantic 校验会直接放行。
4. `StoryPlanningService._ensure_episode_item_short_drama_fields` 会把缺失的阶段阻力、阶段兑现和压力升级替换成通用句，并在缺少场景蓝图时调用 `_fallback_episode_scene_execution_plan`。这会把规划缺口伪装成完整执行计划。
5. `ApprovedEpisodePlanContext` 对缺少场景蓝图保持兼容，并照常编译 `layer_contracts`；正文 Prompt 中“若存在 scene_execution_plan”也会让缺失蓝图变成合法分支。
6. `episode_roadmap_quality_issues` 当前只覆盖场景计划缺失、进出状态重复和少量职责重复，没有阻断 `protagonist_cost`、逐场信息变化、逐场代价和禁止改写项缺失。
7. 连续性确认包、记忆回忆和批准故事节点均有可选路径；即使本集没有完整的来源事实，正文请求仍可能生成。

还有一个必须优先修正的设计矛盾：当前分集规划 Prompt 要求模型不要返回 `scene_execution_plan`，服务端随后再通过 `_fallback_episode_scene_execution_plan` 从摘要字段推导场景。这等于把最需要编剧判断的部分延迟到了正文阶段。面向快速正文模型时，应改为强模型一次返回完整逐场设计，服务端只做校验、引用闭合和合同编译。

这些路径的共同问题是：默认值或兼容分支改变了“缺数据”的含义。它们适合读取历史项目，不适合新项目进入快速正文模型。

## 以提示词为主的改造方式

前置阶段先采用强模型一次性生成完整结构，Prompt 必须包含四段：

1. **任务边界**：明确本阶段只负责什么，不负责什么；禁止把未决问题伪装成已决定事实。
2. **字段合同**：逐字段写出内容要求、长度范围、引用格式和允许的 `unresolved` 条件。
3. **自检清单**：在返回 JSON 前逐项检查角色引用、因果顺序、状态变化、来源集数、禁止改写项和数量一致性。
4. **失败协议**：不能完成时返回稳定的 `review_required` 结构和缺失字段，不返回通用套话，不调用正文模型兜底。

其中分集规划 Prompt 必须明确要求模型一次生成完整的 `scene_execution_plan`，每场同时填写目标、阻力、可见行动、信息变化、人物选择、代价、证据要求、转折、退出状态和禁止改写项。模型不能先输出摘要再让正文模型自行补场。

## P0 的实际代码修改

按当前开发合同直接收紧，旧项目通过重新生成或迁移适配：

1. 路线图禁止使用通用阶段默认句；缺失时返回 `review_required`，不保存为可批准计划。
2. 路线图必须包含逐场执行蓝图；删除 `_fallback_episode_scene_execution_plan` 的生产用途。缺失时自动触发一次强规划模型的“场景蓝图补全”，补全通过后继续，补全仍不完整才阻断。
3. 正文生产 API 在发起正文模型请求前，要求 `approved_episode_plan`、逐场蓝图和连续性执行包齐全；缺失时先执行一次有界规划补全，不能让正文模型承担补设计工作。
4. 新增确定性 `execution_ready` 检查，检查字段完整性、占位句、引用版本、进出状态、场景计数和不可修改事实。
5. 只有配置为 `fast_executor` 的策略才强制执行 `execution_ready`；强模型策略可以进入 `review_required` 修复流程，但也不能静默生成正文。
6. Prompt 继续作为第一道质量边界，Pydantic 和确定性检查只负责发现漏项和阻断，不把编剧判断伪装成分数。

## 验收方式

必须证明四件事：

- 不带批准分集计划的正文请求：零模型请求，明确报错；
- 缺少任一逐场字段的路线图：停在 `review_required`，不触发正文；
- 完整路线图：快速模型只收到执行包，不收到整部未筛选 Story Bible；
- 同一完整路线图分别交给强模型和快速模型，二者的事实、场景结果和人物选择一致，差异只允许出现在语言和表演细节。

## 目标架构中的职责

| 层 | 唯一职责 | 不应承担 |
| --- | --- | --- |
| 输入评估 | 识别范围、缺口、来源和未决问题 | 替作者决定关键剧情 |
| Story Bible | 固定长期事实、人物行为宪法、世界限制和全剧方向 | 按集写正文或临时补事实 |
| 剧情树 | 分配宏观因果运动、故事线责任和节点交接压力 | 直接代替分集场面设计 |
| 分集规划 | 把一个叶节点编译成逐集、逐场执行规格 | 只写宣传式摘要 |
| 连续性包 | 提供本集相关的事实、状态、伏笔和关系债 | 把未发生的内容写成既定事实 |
| 正文模型 | 实现已批准的场面、动作、对白和节奏 | 决定主线转折、关键秘密和关系结论 |
| QC | 判断结构、连续性和编剧质量是否通过 | 用默认句掩盖规划缺口 |

## 分阶段修改

### 第一阶段：建立前置状态机

新增一个可计算的前置成熟度，不改变现有 `draft`、`approved` 等历史状态：

- `incomplete`：有缺字段或未决关键事实；
- `design_ready`：故事和因果设计足够进行人工审批；
- `execution_ready`：逐场规格和连续性包足够交给正文模型；
- `script_ready`：正文合同、来源版本和生成策略均已锁定。

成熟度只能由确定性检查计算，不能由模型自己声称“已完成”。所有缺口输出稳定的 issue code，供前端显示和测试断言。

### 第二阶段：补齐分集执行字段

在 `EpisodeSceneExecutionBeat` 和批准后的上下文中增加向后兼容字段：

- `opposition`：阻力的具体来源；
- `information_shift`：场景前后谁知道了什么、误会了什么；
- `choice_or_cost`：本场人物选择和紧接着的现实代价；
- `evidence_requirements`：正文必须演出的动作、对白、屏幕或道具证据；
- `forbidden_changes`：禁止新增、提前、取消或反转的事实。

所有进入当前活动工作流的计划必须填写。旧项目若缺少这些字段，直接标记为需要迁移并重新生成；不再把它们作为可继续生产的 `legacy` 蓝图。

### 第三阶段：收紧分集规划质量门禁

把现有 `episode_roadmap_quality_issues` 扩展为两组检查：

**阻断项**：

- 场景数量与执行计划不一致；
- 任一场缺少目标、阻力、信息变化、可见行动、结果或证据要求；
- `entry_state` 与 `exit_state` 相同；
- `protagonist_decision` 没有对应的 `protagonist_cost` 或 `dramatic_unit`；
- 使用系统默认套话作为阶段阻力、兑现或压力升级；
- 禁止改写事实与本集揭示义务冲突；
- 连续性引用不存在或来源版本不是当前批准版本。

**警告项**：

- 相邻集重复同一 `scene_engine`；
- 对白或动作预算偏离集型软目标；
- 本集没有关系变化或信息优势转移；
- 结尾钩子只重复本集摘要；
- 本集与最近 5–10 集的开场、揭示或结尾机制过于相似。

阻断项必须停在 `review_required`；警告项可以由作者确认后继续。

### 第四阶段：生成独立的连续性执行包

正文请求不再直接接收整部 Story Bible，而接收按本集编译的 bounded packet：

- 已批准的本集场景规格；
- 出场人物当前目标、限制、知识状态和关系状态；
- 本集需要使用的道具、地点和时间状态；
- 只与本集相关的伏笔和故事线义务；
- 每条事实的来源集数和版本；
- provisional 内容与禁止模型自行确认的事项。

编译器应在发送模型前完成引用闭合检查，避免把无关百科信息或尚未发生的未来事实注入正文模型。

### 第五阶段：把快速模型变成显式策略

在 `GenerationStrategy` 增加正文模型等级或等价策略标识：

- `strong_planner`：允许处理设计缺口和有限修复；
- `fast_executor`：只接受 `execution_ready` 及以上的计划；
- `fast_executor` 不得通过自动重试绕过前置门禁；
- 快速模型出现关键事实偏移、场景无结果或主角选择缺失时，自动降级为人工复核或切回强模型。

模型等级是策略属性，不由前端单次请求随意覆盖。这样可以避免用户无意中把未成熟路线图送入低能力模型。

### 第六阶段：前置链路的测试矩阵

每次修改至少验证以下路径：

1. 合法输入 -> Bible -> 剧情树 -> 分集执行规格 -> 快速正文准入；
2. 缺少场景阻力 -> 触发一次强规划补全；补全成功后进入正文，补全失败才阻断，且正文模型请求为 0；
3. 使用默认套话 -> 阻断；
4. 连续性来源版本过期 -> 阻断，提示重新生成受影响下游；
5. 快速模型输出关键事实偏移 -> QC 阻断并切回强模型；
6. 旧版本没有新增字段 -> 标记迁移必需，补齐后才能继续；
7. 保存、恢复、幂等重放 -> 计划和连续性包指纹一致，零重复模型请求。

## 实施顺序

### P0：先做

- 新增前置成熟度计算器和稳定 issue codes；
- 补齐逐场执行字段；
- 在正文入口增加 `execution_ready` 阻断；
- 为新门禁增加单元测试和 Mock 全流程回归。

### P1：随后做

- 前端显示每集缺失的执行字段和来源；
- 生成连续性执行包并显示其来源集数；
- 增加相邻集机制重复和人物选择缺失的警告；
- 让快速正文策略只读取执行包。

### P2：最后做

- 真实模型 A/B：强模型规划 + 快速正文，对比强模型全链路；
- 固定不同题材的至少 10 集人工盲审；
- 根据事实偏移率、场景补写率、人工修改量和耗时决定快速模型是否扩大使用范围。

## 成功标准

这次优化成功的标志不是正文平均字数增加，而是：

- 快速正文模型不再需要自行补写关键因果；
- 关键事实偏移在发起正文请求前或首次 QC 时被阻断；
- 人工修改主要集中在语言、节奏和表演细节，而不是重做剧情；
- 同一批准计划可被不同正文模型稳定实现；
- 失败可定位到具体前置字段，而不是笼统地归因于“模型不够聪明”。

## 第一步落地状态

当前运行时已经接入场景执行蓝图补全和正文准入门禁：

- 单集生成、分块生成和分集修订会优先要求强规划模型返回完整
  `scene_execution_plan`；缺失或局部不完整时追加一次边界明确的补全调用。
- 旧适配器若不支持补全协议，系统仍可生成供强正文模型使用的本地降级蓝图，
  但会写入 `execution_ready=false`，不会伪装成模型已审阅的蓝图。
- `GenerationStrategy.model_tier=fast_executor` 的正文请求在模型调用前检查
  批准分集计划、场景数量/编号及逐场执行字段，任一缺项都会被硬门禁拒绝。
- 快速正文提示词只允许扩写批准蓝图，不允许重新设计场景结构或猜测缺失合同。

开发阶段仍可用强正文模型处理兼容数据；只有补全成功并标记为
`execution_ready=true` 的新规划才可切换到快速正文模型。
