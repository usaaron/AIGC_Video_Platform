## 本轮新增的诊断证据

首个请求在 9.305 秒收到 HTTP 200 响应头，9.307 秒收到首个响应体字节。适配器结束日志确认此前解析了 12,535 个文本 delta 字符，随后读取超时，未记录终止原因。

这次可确认等待发生在连接建立后的初稿响应阶段，而且已经收到模型文字；不是完全没有响应，也没有进入正文编辑器。12,535 是结构化响应文本字符，包含 JSON 字段和其他元数据，不能当作有效剧本正文字符数。没有保存完整响应原文，因此不能据此判断部分 JSON 是否可修复，或审阅其语义。日志的可见推理字符为 0，也不能推断内部没有消耗推理 tokens。

第 31 号修复解决的是收到明确结束事件后继续等待。本次首请求因读取超时退出，没有可证明已收到终止事件的记录，所以仍有长请求无法完成的问题。不能由本次失败认定上一轮修复无效，也不能说海外路径已经恢复稳定。

初稿服务随后调用 `initial_fallback_llm_adapter` 做非流式恢复；依赖装配将它接到 `SCRIPT_REPAIR` 角色。CLI 的 `--script-reasoning-effort medium` 仅修改海外正文主角色，该恢复角色保留 high。因此本轮是“主路线 medium + 恢复路线 high”，不是所有模型阶段统一为 medium 的实验。第二次请求的 HTTP 524 及 HTML 错误页说明此次非流式恢复也失败，不能把切换传输方式视为已验证的解决方案。

meter 对请求 2 记录的 `outcome=completed` 表示 HTTP 响应体正常读完，不代表生成成功；业务路由日志明确记为 `provider_gateway` 失败。请求 1、2 没有 usage，请求 3 被中断，所以总计 3 次用量未知。原始统计和中断状态均保留，没有改写成成功。
