# 作者修改要求的冲突审阅

日期：2026-09-12

本轮在既有正文修改流程中补充作者决策，不替换原有提示词体系。依据是本次问答确认的原则：以作者最新明确要求为修改目标，系统说明与已有设定的冲突和影响，由作者决定处理方式，不默认勾选方案。

## 交互与边界

1. 作者提交正文修改要求后，先审阅其与已有正文、规划、人物知情及动机的实质冲突。普通润色继续生成修改候选；新颖题材、安静节奏或缺少反转不能成为冲突理由。
2. 冲突报告展示可核对的原文依据、作者目标与影响，并提供契合故事的处理方案。服务端校验引用位置与原文摘录，用户的新要求本身不能被引用为旧设定。
3. 方案不排名、不预选。用户可以选择方案、补充自己的处理方向、暂不处理或撤回要求。补充方向需要重新检查影响，不能忽略补充文字直接采用旧方案。
4. 补足本集因果的方案生成待审正文候选，仍由作者确认采用；确认方案不等于自动采用正文，也不豁免连续性检查。
5. 修改已确认上游设定的方案明确告知将建立独立修订版。新总纲以原批准总纲为基础局部修订，保持待审状态；新版须重新确认总纲和规划。原项目及原稿保留，旧正文结果、连续性记忆和集规划不自动进入新版。

当前版本的规划在正文生成后会锁定，因此使用独立修订版承接上游修改。该实现会要求重新确认完整规划，尚未提供同一项目中按依赖范围自动重算部分后续集的能力。

## 一致性与恢复

- 冲突报告通过已有文档仓储持久化，并绑定源正文、规划上下文、总纲版本和修改要求。用户确认的报告与方案必须和服务端已保存内容一致。
- 页面保存待处理要求和用户填写的方向，关闭窗口或重载页面后可继续处理。源正文或规划发生变化时需要重新审阅。
- 修订版生成完成后才在一个事务中写入新项目、总纲、工作区及请求凭据。提交前复核原项目的批准总纲版本及工作区版本；生成或写入失败不留下半成品项目。
- 同一确认请求重复提交时返回已建立的修订版，不重复生成或覆盖新版后续编辑。
- 新修订工作区首次建立与实际输入相符的总纲编辑基线；后续重试保留新版自己的输入签名，并对齐最新总纲版本与状态，再同步工作区，避免误判输入过期或展示旧稿。
- 最新确认的修订决定仅在授权范围内优先于旧决定。相冲突的旧值保留为历史参考；无关决定和作者明确暂缓的事项继续有效。

## 涉及代码

- `backend/app/modules/script_engine/author_conflict_models.py`、`author_conflicts.py`：冲突结构、证据与确认校验、审阅提示词。
- `generation_service.py`、`prompt_builder.py`、`targeted_revision.py`：正文修改前审阅、候选生成及作者要求优先级。
- `author_revision_service.py`、`backend/app/api/routes/author_revisions.py`：独立修订版、版本校验、原子保存与重试恢复。
- `story_planning_service.py`：新旧已确认决定的局部优先级。
- `frontend/components/author-conflict-dialog.tsx`、`script-workspace.tsx`、`frontend/lib/author-conflict.ts`：选择、补充方向、待处理状态、候选审阅和修订版入口。

- 统一后端首轮全量回归：1660 项通过、1 项跳过；最后的总纲版本重试修复另有 2 项定向测试通过。
- 作者冲突、上游修订及新旧决定优先级的定向回归：40 项通过。新增真实 HTTP 修改审阅 → SQLite 持久化报告 → 上游修订接口贯通测试：2 项通过。
- 前端最终全量测试 440 项通过；本轮定向测试 9 项通过，TypeScript 与 OpenAPI 一致性检查通过。
- Playwright：5 个主要场景在桌面 1440×900 和手机各运行一次，10 项通过，覆盖不预选、暂缓与刷新恢复、补因果候选、自定义重审失败恢复、过期拒绝和上游修订。输入基线修复后，上游修订两端复测通过；手机按钮排版修复后再次复测并人工查看截图，文本完整、操作可达。
- 运行服务已统一重载，存活与就绪检查正常；重载前后的现有项目数据版本与校验值一致。

本轮使用离线模型替身和临时测试数据库验证状态与协议，不据此承诺真实模型能识别所有语义冲突。原有首次正文生成中的模型误写修复仍沿用原流程，本轮交互入口是作者主动提交的正文修改要求。
